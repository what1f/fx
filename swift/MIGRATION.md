## Target

Build a Swift package that runs the existing fx Zig agent core in process through a C ABI. Keep model orchestration, compaction, journal formats, and recovery decisions in their current Zig owners. Provide Swift interfaces for engines, turns, tools, streaming, sessions, and persistence.

The first qualification platform is macOS arm64 with Swift 6.2 or later. Linux and other Apple targets require their own build and runtime evidence. iOS support is not implied by a macOS build.

## Architecture

1. Extract the native runtime from the Node-API entry point into a shared Zig owner. Preserve queue limits, attachment limits, fetch cancellation, and shutdown rules.
2. Expose that runtime through a versioned C ABI with opaque handles and explicit byte ownership. The Node backend continues using the same runtime.
3. Implement a Swift transport and JSON-RPC client. Bridge HTTP through Foundation, tools through async closures, and output through asynchronous streams.
4. Provide `FxEngine` for one conversation. Add `FxAgent`, `FxSession`, and durable storage without substituting a JavaScript implementation for Swift behavior.
5. Add a JavaScript test adapter that forwards public operations to a Swift executable. Forward tool requests back to test closures. Preserve upstream assertions and use the actual Swift SDK for all engine behavior.

## Swift design principles

Use typed configuration, events, results, and errors with async/await and AsyncSequence. Keep JSON-RPC and JSON field names internal, except JSON values for tool schemas and dynamic tool inputs. Use actors where mutable state requires serialization. The JavaScript adapter translates API shape and reuses assertions; it must not implement missing Swift behavior. Target the current protocol only. Do not copy historical JavaScript compatibility branches or platform fallbacks.

## Contracts

C calls report errors without unwinding across the ABI. Buffers have explicit lengths, and their producer supplies the matching free operation. Handles have a documented close and destroy order. No callback may retain an unowned Swift object. A single owner serializes runtime access and shutdown.

Swift values crossing concurrency boundaries are Sendable. Cancellation must reach model transport and tool tasks. Closing rejects pending requests, terminates event streams, stops effects, and joins runtime work. Streaming uses bounded buffering and pauses its producer until the reader makes space. Oversized frames fail explicitly.

Persistence preserves ordered append, expected cursor checks, durability barriers, version errors, and uncertain tool outcomes. Recovery must not blindly repeat a write. Checkpoint compatibility with JavaScript is a separate acceptance gate from ordinary Swift save and load.

### Remaining original SDK integration work

Acceptance follows the original libfx capabilities. SQLite persistence and injectable host storage remain in the Swift SDK. Adding an unrelated database backend is not a migration requirement. The PostgreSQL experiment is preserved on `experiment/libfx-postgres` and excluded from this package and its dependencies.

The original World/Vercel integration remains a distinct contract: Workflow event CAS and binary streams, Queue delivery and acknowledgement, credentials and delivery authority, request deadlines and inline backstops. Identify its portable durable behavior separately from deployment-specific integration, and retain missing behavior or evidence explicitly. Local SQLite and host-protocol fixtures do not prove deployed Vercel service behavior. Do not substitute a new database product for this qualification.

The portable HTTP wake entry now uses optional `LibFxHTTP` and Apple HTTPTypes. Queue publications carry accepted input IDs through prompt, steer, resume, and cancellation; HTTP publishers encode the received wakeup without querying storage. The handler checks durable membership, routes within the explicit store, and reuses the current worker. Native tests cover the original core HTTP scenarios at 1824, 2013, 2039, 2064, 2096, and 2113, including forged bodies, absent inputs, immutable ownership, store isolation, and unavailable workers. This proves portable equivalents, not the original Vercel handler or JS global registry.

Release recovery now retries a nonsemantic host failure once without replaying executor effects. `ReleaseRetryTests` reproduces the core:517 failure boundary and verifies scripted continuation, a real native tool executed once, exhausted retry, cancellation, and fencing. SQLite retains local ownership resources when its release write fails. General storage retries and queue-authorized recovery after a persistently failed release remain separate from this narrow recovery path.

The remaining behavior audit identifies two additional implementation gaps: authenticated queue redelivery must be able to replace its prior unexpired owner, and live agents with the same name and store must reject incompatible configurations while allowing compatible copies to close independently. Keep those contracts in the acceptance matrix. Existing TTL recovery and same-name replica tests do not establish them.
