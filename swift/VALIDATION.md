# Swift SDK validation

This is an implementation milestone, not full libfx parity or a release qualification.

## MCP integration

The optional `LibFxMCP` product uses the official Swift MCP SDK 0.12.1. Eleven tests cover a host-configured client, catalog validation and name collisions, resource and prompt composition, UTF-8 instruction bounds, structured results and image/error conversion, cancellation and late replies, cancellation before client registration, setup cancellation, pending-call shutdown, and cancellation from a real Zig-backed `FxEngine` reaching the MCP server. Protocol tests use the actual official client and a scripted transport. The native engine test sends one model request and a held MCP tool call, cancels the turn, and observes a remote cancellation notification without another model request.

All assertions in the upstream `test-mcp-adapter.mjs` pass for native stdio and HTTP text, images, image-only, and image-error modes. Swift owns catalog processing, context composition, result conversion, and request cancellation. JavaScript forwards the fixture client's operations and retains its transport. One explicit shape normalization expands the stdio fixture's nonstandard prompt content array into single-block messages, preserving every block and role. The independent Release consumer imports `LibFxMCP`, uses the official HTTP transport against a local MCP server, reads tools/resources/prompts, calls a tool, and closes the adapter. This is local fixture evidence, not a production MCP service or authentication qualification. The Release consumer also drives a tool through a real Zig engine and the local MCP HTTP server, then checks the owning tool identity and the start/end span pair.

## Input waits

Six native tests cover all four request kinds, accepted and denied decisions, host-specific timeout classification, original error identity, observer errors, one shared UTF-8 budget per event, array limits, cancellation before and during an effect, late answers, retained inactive scopes, and mixed MCP/wait invalidation. Tests confirm that full results remain unchanged, private error descriptions are omitted, and cancellation produces only one terminal event.

The durable child-engine test also wraps an input effect and verifies its parent tool scope. The independent Release consumer uses the public wait API inside a tool executed by the real Zig engine, retains the full 128 KiB tool input, and checks start/end identifiers, captured prompt and answers, and the successful decision. This is scripted host-input evidence, not a UI or real-user approval test. The test bridge now forwards input waits to the actual Swift scope. `input-observation.mjs` compares both SDKs across capture settings and failing observers, preserves cyclic host objects and original errors, and checks one cancelled terminal event despite a late answer. The complete upstream hooks owner remains pending: its unchanged run currently stops because diagnostic callbacks incorrectly enable hooks in the bridge. MCP scope forwarding and fixture-runtime descendant assertions also need Swift-backed execution.

## Environment

Local checks ran on macOS arm64 with Swift 6.4, Zig 0.17.0, and Node.js 25.9.0. Upstream SDK CI requires Node.js 24; the local Node runs do not replace that gate. The C library targets macOS 14. Runtime qualification for x86_64 remains pending.

The Swift package requires Swift 6.2 or later. CI selects Xcode 26.3 on macOS 15. `Package.resolved` records Collections 1.3.0 because the newer 1.7.3 release requires Swift 6.4; it enters resolution through the MCP package's server-side NIO dependency. This lockfile choice does not impose an upper Collections version on consuming applications. Local manifest inspection found no resolved package requiring a tool version above 6.2. An actual Swift 6.2 compiler run still requires CI evidence.

The agent/session implementation has 20 native tests. They cover durable ordered intake, historical message-ID deduplication, per-reader replay, scoped queued cancellation, graceful close, competing local connections and agents, stale-owner rejection, snapshot rollback, wrong-agent rejection, persisted tool context and public identities, and configuration failures before storage or network access. Two recovery fixtures distinguish a started input with no core dispatch from a completed core turn with no saved host result. The former runs normally; the latter returns `.unknown` without another model call. These fixtures simulate those boundaries in process; they are not SIGKILL qualification of the new session store.

`FxSessionStore` stores intake, events, and core journals in one SQLite database. Ownership checks and writes share an immediate transaction, following [SQLite's documented isolation rules](https://www.sqlite.org/isolation.html). A separate local file lock covers the worker lifetime. The Release consumer also imports the public agent/session API, runs a durable turn, accepts steering, configures a delivery policy, replays its events, and checks historical-ID deduplication. Full upstream durable-session coverage remains pending.

Five native steering tests cover streamed text interruption, idle execution, deduplication and prompt/steer ID conflicts, multiple unplaced inputs after cancellation, image handoff with later text, and steering from another store connection and agent. Two additional store tests verify that steering marks roll back with a failed journal append, retrying an old append does not reapply its marks, and migration from schema version 1 preserves queued inputs and their options. The store is now at schema version 3. Acceptance, placement, and delivery-step marks commit in the same transaction as their core journal records.

Five native delivery tests check duration validation, four cooperative deliveries with one public turn and three unique tool executions, bounded cancellation of a stalled model followed by a usable session, persisted cutoff counts across reopen and step changes with stale-owner rejection, and cancellation of an open turn between deliveries. `Duration` expresses the policy; [ContinuousClock](https://docs.swift.org/latest/documentation/swift/continuousclock/) measures the active cutoff without wall-clock adjustment. The same active cutoff now covers engine preparation, including catalog and credential lookup. The cutoff requires a nonzero reserve; synchronous intake and SQLite operations do not gain a forced interruption deadline.

Seven preparation tests verify catalog timeout with the original input retained for explicit resume, cancellation of subscription credential lookup, cancellation after an uncooperative journal load returns, joining a cancelled load before reporting timeout, an already-expired deadline before loading or allocation, repeated open/deadline races without native slot exhaustion, and journal-read failure without a false completed result. The Release consumer exercises timeout and same-ID resume through the public API. `preparationTimedOut` leaves accepted input pending, releases worker ownership, and does not automatically retry. The implementation uses a [Swift task group](https://docs.swift.org/latest/documentation/swift/taskgroup/) and closes any engine that finishes after losing the deadline race. HTTP, credential, and asynchronous persistence callbacks must cooperate with cancellation: the group waits for its children to exit, so a callback that ignores cancellation can delay the reported timeout.

Native observation tests verify metadata on exports and snapshots, continued restoration after a change, stable tool identity despite dictionary and tool ordering, changed model and replay flags, credential omission, and containment of an observer error. New-agent seed validation suppresses duplicate notices; the worker that restores the seed emits the notice. Agent interval tests check explicit zero and nil settings and rejection of negative intervals.

Four session checkpoint tests cover read-only export with images, export during a live worker, exporting an unused view without creating data, and invalid seeds rejected before intake. The Release consumer exports a session and seeds another agent through the public API.

The independent Release consumer also exercised the default Foundation client against a local HTTP server. It completed an authenticated custom-provider turn, rejected authenticated and token-body 307 redirects, and verified that the redirect target received no request. The Release consumer also used the public subscription API for a Grok turn. The custom-provider conformance scenario compared JavaScript and Swift engine requests, host-tool round trips, missing credentials, rejected keys, and plain and JSON-escaped credential redaction.
